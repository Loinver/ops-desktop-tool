# Ops Desktop 全局功能闭环审计与扩展路线

- 审计日期：2026-08-07
- 审计范围：Electron 主进程、Preload/IPC、Vue Renderer、后台调度器、本地存储、安全边界、Node/Renderer/Electron 测试
- 当前结论：**核心运维链路已形成较完整闭环；跨模块统一感知能力本轮已补强；统一任务编排、统一审计和更细的自动修复仍是下一阶段重点。**
- 提交状态：**本轮没有创建 Git commit，所有修改均保留在工作区供人工检查。**

## 1. 执行摘要

当前应用已经不是简单的本机工具集合，而是一个围绕以下主链路组织的本机优先运维工作台：

> 发现问题 → 聚合事件 → 分析问题 → 执行操作 → 验证结果 → 记录历史或恢复状态

审计结论如下：

1. **系统发布、模型可靠性、统一运维事件、HTTP/TCP 自动化巡检、Node 服务关注、数据备份恢复**已经具备较完整的业务闭环。
2. **AI Provider、质量评测、知识库、日志分析、AI 对话和安全工作流**已经能形成可用闭环，但执行型能力仍偏保守，符合本机安全优先定位。
3. **快捷启动、剪贴板、图像生成**具备配置、执行、结果反馈和历史/删除等工具型闭环。
4. 原仪表盘描述为统一查看自动化和待处理事件，但数据和页面主要集中于发布、模型巡检与备份，存在“能力已在下层形成，但首页看不到”的断点。
5. 本轮已自动补齐仪表盘的**待处理事件、自动化巡检、Node 服务关注和巡检覆盖**，并提供按事件来源跳转、首次加载失败隔离、刷新失败旧数据标记与重试。
6. 仪表盘 IPC 已进一步收紧：最近事件只返回页面必需白名单，不向 Renderer 发送原始错误描述、属性、时间线或指纹。
7. 未发现必须阻断使用的 P0 级功能缺口。剩余重点是跨模块任务中心、统一操作审计、IPC 调用方校验、实时刷新和更广泛的页面级测试覆盖。

## 2. 审计方法与闭环判定标准

### 2.1 审计方法

本次检查包含：

- 盘点 Renderer 路由、功能菜单与所有页面入口；
- 检查主进程 IPC、工具模块、后台调度器和本地数据文件；
- 跟踪发布、模型、自动化、Node、备份产生统一事件及自动恢复的调用路径；
- 检查敏感字段是否进入 Renderer、凭证是否经 `safeStorage` 保存；
- 检查确认弹窗、路径边界、回滚、恢复点和错误反馈；
- 执行完整格式、Lint、Node 测试、Renderer 测试、Electron E2E 和生产构建；
- 启动隔离 Electron 实例，在 1400×900 与应用最小 960×700 窗口下检查布局、滚动、溢出和关键内容。

### 2.2 闭环判定标准

一个执行型模块至少检查以下环节：

1. 是否能完成配置或输入；
2. 是否能实际执行；
3. 是否能显示成功、失败和错误原因；
4. 是否能保存结果、历史或状态；
5. 是否支持重试、回滚、恢复或撤销；
6. 异常是否能进入统一事件，恢复后是否能闭合事件。

工具型模块不强制要求统一事件，但应至少具备“输入/配置 → 执行 → 反馈 → 管理历史或状态”。

## 3. 功能闭环总览

- **完整闭环**：主要动作、结果、历史和恢复链路齐全；

- **工具型闭环**：模块定位是查看或桌面效率工具，不以告警恢复为核心目标。

## 4. 已确认的关键跨模块闭环

### 4.1 模型可靠性闭环

1. 从 CC Switch 读取 Provider、模型和端点；
2. 使用真实协议请求验证模型；
3. 保存测试历史和趋势；
4. 定时巡检在主进程后台执行；
5. 异常生成统一事件和桌面通知；
6. 模型恢复后自动关闭对应事件；
7. 仪表盘和运维中心展示当前风险并提供处置入口。

### 4.2 自动化巡检闭环

1. 创建 HTTP 健康检查或 TCP 端口任务；
2. 手动执行或由后台调度器按间隔执行；
3. 保存最近结果、运行历史和下次执行时间；
4. 失败时生成统一事件并按稳定指纹去重；
5. 后续成功时自动恢复对应事件；
6. 运维中心负责确认、解决和查看时间线；
7. 本轮新增仪表盘摘要和巡检覆盖入口。

### 4.3 Node 服务闭环

1. 扫描本机 Node.js 监听端口；
2. 用户明确关注需要监测的端口；
3. 主进程周期性检查关注项；
4. 停止监听时生成统一严重事件；
5. 恢复监听后自动关闭对应事件；
6. 页面可安全结束或强制结束进程，并在破坏性操作前确认；
7. 本轮新增仪表盘在线、离线和未知状态摘要。

### 4.4 系统发布闭环

1. 管理多环境发布 Profile 和 SFTP 凭证；
2. 发布前执行路径、连接、文件和远端能力预检；
3. 支持上传、续传、比较、删除、创建目录及 ZIP 部署；
4. 发布后执行健康检查；
5. 保存发布历史和远端备份信息；
6. 失败或需要恢复时执行回滚；
7. 发布、失败和回滚结果进入历史及统一事件体系。

### 4.5 数据备份闭环

1. 按功能分类收集本地数据；
2. 使用 AES-256-GCM 创建加密备份；
3. 支持完整性校验、恢复和自动备份历史；
4. 恢复前创建本机恢复点；
5. 可回滚恢复操作；
6. 自动备份按保留策略清理旧文件；
7. 备份失败和恢复状态可进入事件体系；
8. 仪表盘显示安全裁剪后的备份健康信息，不暴露路径和密码。

## 5. 本轮已自动开发的功能

### 5.1 全局待处理事件进入仪表盘

新增内容：

- 活跃事件、严重事件和未读事件摘要；
- 最近 6 条未解决事件；
- 来源、严重级别、状态、重复次数和最近发生时间；
- 点击事件按来源进入系统发布、模型可靠性、Node 服务、数据管理、AI 运维或运维中心，并携带事件参数；
- IPC 仅返回展示所需字段，不传递事件原始 `description`、`attributes`、`timeline`、`fingerprint` 等内部详情。

### 5.2 巡检覆盖进入仪表盘

新增四类覆盖状态：

- 模型定时巡检；
- HTTP/TCP 自动化任务；
- Node 服务关注；
- 本地数据备份。

每类能力显示“未配置、正常、等待首次运行、告警或异常”状态，并可跳转到对应管理页面。

### 5.3 仪表盘加载错误闭环

新增：

- 首次加载失败时只显示未知状态，不把零值渲染为健康；
- 刷新失败时保留上次成功数据，并明确提示当前数据可能过期；
- 具体错误信息；
- “重新加载”按钮；
- 保留原有消息通知反馈。

### 5.4 后端安全聚合

仪表盘新增聚合数据均在主进程计算：

- 事件仅返回页面必需的稳定安全字段，不包含原始 `description`、`attributes`、`timeline` 或 `fingerprint`；
- 自动化只按启用任务的最近结果统计健康、失败和待运行；
- Node 服务只按启用关注项统计在线、离线和未知；
- 不把任务目标、事件内部属性、凭证或本机敏感路径直接送入 Renderer。

## 6. 仍需处理的主要缺口

### P0：阻断性问题

本轮静态审计和完整测试中**未发现 P0 级阻断问题**。

### P1：建议优先推进

#### 6.1 统一任务中心

当前模型巡检、HTTP/TCP 自动化、Node 检查和自动备份分别由不同调度器维护。它们都能运行，但缺少统一视图来回答：

- 当前有哪些后台任务；
- 哪个正在执行、排队、暂停或失败；
- 下次执行时间；
- 最近耗时和连续失败次数；
- 是否可一键暂停、立即执行或查看关联事件。

建议新增 `/task-center`，先做只读聚合，再逐步统一操作接口。

#### 6.2 统一操作审计

发布和事件已有专用历史，但 AI 工作流、Provider 切换、知识变更、进程终止、备份恢复等操作没有统一审计视图。

建议记录：操作者、本机、动作、输入摘要、确认状态、结果、耗时、关联事件/任务、可恢复点。敏感值必须脱敏或只保存引用。

#### 6.3 IPC 调用方统一校验

应用已启用 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true` 和 `webSecurity: true`，且 Preload 采用显式 API。但审计中未见所有 `ipcMain.handle` 统一经过 Renderer URL/发送方校验，仅少数位置做了窗口归属判断。

建议增加统一注册封装，在进入业务处理器前校验发送方属于当前受管窗口和允许的 Renderer URL。这是纵深防御，不代表当前已发现可利用漏洞。

#### 6.4 仪表盘实时性

当前仪表盘主要在进入页面和手动刷新时读取数据。统一事件已有变化通知基础，可进一步：

- 事件变化时局部刷新摘要；
- 后台任务完成时刷新对应覆盖项；
- 页面失焦时降频，恢复前台时立即同步；
- 显示“数据生成时间”和过期状态。

#### 6.5 页面级自动化测试不足

当前 Renderer 测试主要覆盖菜单、路由、主题和侧边栏；Electron E2E 覆盖桌面壳与关键路由。核心页面仍需要更多组件或 E2E 回归：

- 仪表盘事件深链和错误重试；
- 发布预检、失败和回滚交互；
- 运维中心事件确认/解决；
- Node 关注与结束进程确认；
- 数据恢复与恢复点回滚。

#### 6.6 异步状态规范继续统一

多数页面已有成功/错误消息，但加载中、空状态、局部失败、重试和按钮防重复提交的表现仍不完全一致。建议继续按页面布局 Skill 建立通用 `AsyncState`、`InlineError` 和 `RetryPanel` 组件。

### P2：中期增强

- 事件维护窗口、告警静默、升级策略和 SLA；
- 多模型质量、延迟、价格和配额综合评分；
- 服务 CPU/内存/重启次数历史；
- 发布灰度、批次、多主机和审批；
- 备份远端副本和灾难恢复演练；
- 知识库版本、重复检测、过期提醒；
- AI 对话多会话持久化、搜索和反馈；
- 应用内更新与版本兼容性检查。

## 7. 推荐扩展路线

### 阶段 A：增强现有闭环（建议优先）

#### A1. 统一任务中心

复用现有四套调度数据，建立统一任务 DTO 和状态视图，不立即重写各调度器。第一版应支持：

- 全部任务、启用状态、最近结果、下次执行；
- 来源筛选和失败筛选；
- 跳转到原模块；
- 在确认后执行“立即运行/暂停”；
- 关联统一事件。

#### A2. 事件 Runbook

基于现有事件、AI Copilot、知识库和安全工作流，形成：

> 事件 → 收集证据 → 推荐 Runbook → 用户确认 → 执行安全步骤 → 自动复检 → 关闭或升级事件

第一阶段只允许页面跳转、只读诊断和现有安全动作，不开放任意 Shell。

#### A3. 统一操作审计

先覆盖高风险动作：

- 发布与回滚；
- 结束进程；
- 数据恢复与恢复点回滚；
- AI 工作流确认执行；
- Provider/凭证变更。

#### A4. 仪表盘实时刷新和筛选

增加来源、严重级别、时间范围，以及事件变化驱动的局部刷新。保留手动刷新作为容错入口。

### 阶段 B：提高诊断与决策质量

#### B1. 变更风险评分

在发布前结合：文件数量、删除比例、关键路径、最近失败、目标环境、健康检查覆盖度，给出低/中/高风险和必须确认项。

#### B2. 模型成本与质量中心

把模型可靠性和质量评测组合为统一评分：

- 可用率；
- P50/P95 延迟；
- 质量用例通过率；
- 请求成本估算；
- 最近回归；
- 推荐默认模型。

#### B3. 本机服务健康历史

在现有 Node 服务关注基础上增加采样历史、连续离线次数、重启记录和可选的受控重启策略。

#### B4. 诊断包

一键导出脱敏诊断包，包含应用日志、系统信息、任务状态、事件摘要和版本信息，便于人工排障或提交问题。

### 阶段 C：从单机扩展到多节点

在保持本机优先的前提下，可选增加轻量远端 Agent：

- 多主机资产与环境清单；
- 远端端口、服务和资源监测；
- 受控命令白名单；
- 主机级事件与任务；
- 凭证只保存在本机或系统密钥链；
- 所有远端写操作必须确认并写入统一审计。

不建议当前直接进入团队协作、支付、复杂权限或云端账号体系，除非产品定位明确从个人/小团队本机工具转向平台化产品。

## 10. 人工检查建议

建议按以下顺序检查：

1. 打开“运维仪表盘”，确认顶部有“待处理事件”和“巡检覆盖”；
2. 创建或运行一个失败的 HTTP/TCP 自动化任务，刷新仪表盘；
3. 分别点击发布、模型、Node、备份或 AI 来源事件，确认进入对应处置页面并带上事件参数；
4. 在 Node 服务页关注一个端口，停止该服务后执行检查，确认事件出现；
5. 恢复服务后再次检查，确认统一事件自动恢复；
6. 检查模型定时巡检、自动化、Node 和备份四个入口是否跳转正确；
7. 将窗口缩到应用允许的最小宽度，检查无横向滚动且所有区域可通过 Workspace 滚动访问；
8. 查看本文件第 6、7 节，决定下一轮优先开发“统一任务中心”“统一操作审计”或“事件 Runbook”。

## 11. 建议的下一轮优先级

如果继续自动开发，推荐顺序为：

1. **统一任务中心（只读聚合版）**：复用现有数据，风险最低、全局价值最高；
2. **仪表盘实时刷新与筛选**：提升当前增强功能的时效性；
3. **统一操作审计**：先覆盖高风险操作；
4. **事件 Runbook 与执行后复检**：把“发现—分析—处理—验证”进一步自动化；
5. **IPC 统一发送方校验**：作为安全纵深改造，分批迁移和测试。
